Nodos externos: TU equipo como salto real (Fase 9)

Hasta ahora el circuito saltaba solo por los contenedores docker del VPS. La Fase 9 añade lo importante: los equipos de los usuarios se unen a la red como nodos personales (peers), quedan registrados en /nodos y pueden entrar a los circuitos. Y, para probarlo con hechos, existe el modo externos: el circuito salta SOLO por equipos de usuarios y sale a internet con la IP pública del nodo externo — no por la del VPS.

Cómo se une un equipo a la red

  1. Registro determinista: con tu primera conexión a la red (o un latido del cliente peer), la API crea tu nodo peer_u<id> (upsert por nombre: el mismo usuario SIEMPRE mapea a la misma fila; nunca desaparece de la lista).
  2. OPT-IN del salto (obligatorio): tu nodo se registra pero NO salta hasta que tú lo aceptes desde el panel (pestaña «Nodos» → tarjeta «Mi equipo como salto» → «✓ acepto ser salto»). Hasta entonces la dirección se FUERZA a ip:0 y el nodo queda fuera de todos los pools, aunque su cliente anuncie un servicio abierto. Puedes revocarlo cuando quieras y el efecto es inmediato (siguiente latido = vuelve a :0).
  3. Servicio opcional: una vez aceptado el salto, si tu cliente anuncia host:puerto de un servicio peer abierto (el script peer/nodo_personal.py en tu máquina), ese puerto entra al pool de saltos. Sin servicio anunciado, el nodo va con :0: se ve en la lista pero NUNCA se elige (_hoppable() lo excluye).
  4. Doble verificación en el sorteo: además del opt-in, elegir_circuito() filtra con JOIN sobre los usuarios: un nodo tipo=usuario cuyo dueño no aceptó (peer_publico=0) no entra jamás en un circuito, ni siquiera con dirección saltable antigua.
  5. Latido: el equipo envía POST /nodos/heartbeat con X-Interno: PEER_TOKEN y nombre peer_* (los contenedores docker usan INTERNAL_TOKEN). Cada latido trae conexiones vivas que reenvía.

Válido no es latiendo: el sondeo TCP es el juez

El heartbeat solo demuestra que el equipo está encendido. La validación REAL (lo que el usuario pidió: «que lo valide mejor») es un sondeo TCP de verdad:

  • Un hilo de fondo en la API sondea cada 15 s (concurrente, no en serie) todos los nodos con puerto real: connect real + medición de lat_ms.
  • El resultado (registrado en ult_ok) es el único pasaporte: un nodo es saltable solo si su sondeo conectó dentro de TTL_OK (≥45 s).
  • Sondeo bajo demanda: si el circuito necesita un nodo «frío», lo sondea AHÍ mismo antes de rechazarlo (sin 503 injustas).
  • /nodos muestra por nodo: ms (latencia), responde (sondeo fresco), sin_ok_s (segundos desde el último OK) y saltable (puerto real + respondió).

El modo externos (puestos para probar con hechos)

POST /connect {"modo":"externos"}        # circuito 100% equipos de usuarios
POST /rotate                              # respeta tu modo al rotar
GET  /me  →  { "circuito": ["peer_u7","peer_u42"], "ip_salida": "90.169.x.x",
                "exit_ip": "90.169.x.x" }
  • El pool se filtra: los contenedores docker del VPS quedan FUERA (tipo=usuario solamente).
  • Flexible: si la red aún tiene pocos externos, se admite un circuito más corto (mínimo 1 salto) para poder probar el mecanismo igualmente. Sin flexible, 503 con el detalle del pool.
  • La IP de salida es la del peer: si el exit es un peer con IP pública anunciada, ESA ES la IP que ve internet (el peer está en su casa, no en el VPS): ip_salida y exit_ip lo muestran, y la comprobación del panel la confirma.
  • Nunca tu propio equipo como salto: el sorteo excluye peer_u<tu-id> del propio circuito.

Privacidad del peer externo

  • El peer no descifra NADA si JENC está activo: reenvía registros cifrados como cualquier nodo.
  • La API no guarda histórico de qué circuito pasó por qué peer ni cuándo: solo la fila de estado actual del usuario.
  • Tu nodo siempre está VISIBLE en /nodos con su alias (si lo pusiste): es el precio de entrar en la red compartida, como en Tor las relays públicas.
