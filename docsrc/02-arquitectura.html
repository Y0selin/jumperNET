Mapa completo del despliegue

Todo corre en un solo VPS (Oracle Cloud, Ubuntu) orquestado con docker-compose dentro de una red docker propia (red_jumper). El único puerto público es el 443 (Caddy); los SOCKS5/HTTP de entrada están publicados aparte para los clientes.

Flujo byte a byte de una petición

  1. Tu cliente habla SOCKS5 con entrada:1080 (o HTTP CONNECT con Basic auth en 1081). GSSAPI y «sin autenticación» se rechazan SIEMPRE: la validación de credenciales hace el resto.
  2. entrada llama internamente a la API (POST /interno/socks_auth, solo red docker) con tus credenciales: la API verifica argon2 y devuelve tu círculo actual (lista de saltos).
  3. La entrada VALIDA el destino además aquí (defensa en profundidad): solo puertos 80/443, bloqueo de IPs privadas/docker/link-local y metadata 169.254.169.254 de Oracle.
  4. Conecta al primer salto con "nodo2,nodo5,destino:host:puerto"\n: Fase 1 en claro entre contenedores de la misma red… y si CLAVE_SALTOS está activa, tu petición ya viaja como PRIMER registro JENC (Fase 8): los nodos intermedios solo ven ruido ChaCha20-Poly1305.
  5. Cada nodo lee la ruta restante, lo recorta a la dir de extrema y reenvía ciegamente ambos sentidos.
  6. El exit descifra JENC (detección automática por prefijo), manda la magia de reconstrucción y abre el TCP a destino real: la web ve IP del exit.
  7. La respuesta vuelve por el mismo camino; hacia el cliente los datos van re-cifrados registro a registro si el circuito es JENC bidireccional.

El plano de control separado del plano de datos

La API (control) NUNCA está en el camino de los datos. Flujos: «cuenta y circuito» (HTTPS→Caddy→API) frente a «bytes de navegación» (SOCKS 1080→nodos→salida). Esto permite: reiniciar la API sin cortar tú tráfico; validar nodos sin tocar reenvíos; y que la API no vea ni un byte de web.

Registro de nodos: 'infra' frente 'usuario'

un ping a la API cada 10 s (POST /nodos/heartbeat con INTERNAL_TOKEN). Desde Fase 9 los equipos de usuarios también latan (con PEER_TOKEN y nombre peer_*) y quedan marcados tipo=usuario: la fila queda visible para siempre (persistencia upsert por nombre determinista peer_u<id>) y y el estado vivo/caído lo decide el latido más el sondeo TCP del validador de fondo. /nodos enseña ms, responde, saltable, tipo por nodo.

Dónde vive cada cosa

  • ~/jumpernat en el VPS: servicios, tests, docker-compose, docsrc, descargas y .env con las claves.
  • /data/jumpernat.db: SQLite del estado (usuarios, nodos, planes). Sin histórico de destinos (regla 4 del proyecto).
  • Panel en GitHub Pages (estático) que habla HTTPS con la API via Caddy /api.
