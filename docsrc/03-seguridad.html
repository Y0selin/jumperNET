Principio rector

Guardamos lo mínimo imprescindible para operar la red, ciframos lo sensible y bloqueamos por defecto. Y, sobre todo: no existe histórico de destinos — la base de datos solo guarda el estado actual del usuario (regla 4 del proyecto).

Cuentas

  • Contraseñas nunca en claro: se guardan con argon2 (hash con memoria). Ni logs ni dumps contienen la cadena original.
  • Sesiones: JWT firmado con JWT_SECRET (en .env fuera de git), caduca en 7200 s (2 h).
  • Login duro: 5 intentos por minuto por IP; al 5.º fallo de una cuenta, bloqueo de 5 min; respuesta genérica «credenciales no validas» para no revelar si el email existe.
  • Registro anti-spam: máximo 3 cuentas creadas por IP cada 5 min (429 más allá) y tope global de usuarios (MAX_USUARIOS, 500).

La red por dentro

  • Solo dos métodos SOCKS5 válidos: usuario/contraseña (0x02). GSSAPI (0x01) e «no-auth» (0x00) se rechazan SIEMPRE — esto no es un proxy abierto.
  • Credenciales = cuenta: email + contraseña de la web, validados contra la API (argon2) en cada conexión; el usuario debe estar conectado (/connect) para tener circuito vigente.
  • Doble filtro de destino: la entrada valida puertos 80/443 y bloquea IPs privadas, redes docker, link-local y la metadata 169.254.169.254 de Oracle; el exit re-valida (defensa en profundidad). Excepción explícita: el destino interno de pruebas web-destino.
  • Cifrado entre saltos: con CLAVE_SALTOS los datos viajan como registros ChaCha20-Poly1305 (JENC): los nodos intermedios ven solo ruido autenticado (ver el post JENC).
  • Tokens de red: INTERNAL_TOKEN para nodos de infraestructura y PEER_TOKEN para los personales de usuarios (nombre peer_*). La API solo escucha en 127.0.0.1:8000 y red docker.

La IP real solo cuando la peticion viene de un proxy de confianza

La API toma X-Forwarded-For únicamente cuando la conexión llega desde PROXIES_CONFIANZA (Caddy en docker: 172.16.0.0/12, 10.0.0.0/8). Un cliente que golpease la API directo no podría suplantar otra IP.

Qué ve la web del panel y qué NO

El panel enseña: cuenta (alias, lema, foto), estado activo, modo (todos/externos), circuito de saltos, IP de salida y última comprobación. No enseña (y no existe): tráfico, DNS, destinos ni histórico de circuitos.

Buenas prácticas del navegador

  • La contraseña del chip PROXY se guarda en localStorage local (nunca en la red) y se enmascara en el log interno.
  • El proxy se aplica a TODAS las sesiones del Chromium (por defecto y persist:jn): ni una pestaña escapa en claro.
  • Los logs internos (= jn://log) limpian credenciales: el correo sale enmascarado.
