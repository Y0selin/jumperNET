Principio: menos superficie, menos sorpresas

La seguridad de JumperNET se construyó por sustracción: cada pieza solo puede hacer lo mínimo que necesita. Estas son las decisiones concretas y el porqué de cada una.

Credenciales y cuentas

  • Contraselas guardadas con argon2 (resistente a GPU). La API nunca ve la contraseña en claro tras el login; los proxies autentican presentándola de nuevo en Basic, que viaja por HTTPS en el salto tú→entrada y por JENC dentro del circuito.
  • Sesiones con JWT en memoria del navegador (no cookie persistente) de 120 minutos renovables.
  • Anti-abuso de registro: límite de cuentas por IP con ventana deslizante (por eso durante los test de carga se reiniciaba la API para vaciarlas).

Lo que los saltos pueden (y no pueden) ver

  • Entrada: conoce TU identidad (te autentica) y el primer salto del circuito. NO ve el destino desencriptado si JENC está activo: solo recibe registros cifrados.
  • Intermedios: reenvío ciego de una conexión identificada por nº de puerto efímero. Sin logging de contenido.
  • Exit: ve el destino final, pero no tú (solo el stream que el circuito le manda). Con JENC activo, además es quien descifra hacia internet y cifra las respuestas.
  • Este "compromiso de confianza" es el mismo que Tor: si TODAS las piezas son del mismo servidor (como aquí), la garantía es educativa/laboratorial, no un anonimato a prueba de estados.

Filtros de destino (anti-SSRF)

Los dos proxis validan cada destino: solo puertos 80 y 443; lista de excepciones declaradas para pruebas internas; bloqueo de IPs privadas, Docker (172.16-172.32), loopback y metadata cloud (169.254.169.254). El exit re-valida tras resolver DNS — porque una consulta DNS que devuelve 127.0.0.1 es la forma clásica de saltarse un filtro de nombre.

Exposición de puertos

Del VPS salen hacia el exterior exactamente: 80 + 443 (Caddy), 1080 (SOCKS5) y 1081 (HTTP). Todo lo demás (API, nodos, wp_db) queda en la red red_jumper sin salida pública. Documentado con iptables/ufw y la Security List de Oracle.

Logs y datos

Entradas y nodos registran líneas operativas (CONNECT host:puerto, HA, auth rechazada) para depurar, SIN contenido de tráfico ni URLs GET. El exit no guarda nada por conexión. Las cuentas viven en SQLite de la API (/data del contenedor), backups manuales del fichero.

Persistencia del cliente

  • Extensión: credenciales en chrome.storage.local de tu navegador, nunca en el servidor.
  • Navegador: cuenta.json en el perfil propio (chmod 600 en Linux) con email, clave y token solo para las credenciales del 407.

Apagado limpio

La red no se «apaga» borrando credenciales: el interruptor corta el circuito y el proxy de la sesión vuelve a direct. La memoria del desconexión borra rutas y salidas. Sin sesión, el panel queda en 401 (verificado).
